01

问题不在 Vite，问题在框架替用户做了多少决定，又能否把这些决定讲清楚。

这轮重构的起点不是换一个构建器，也不是再包一层插件。起点是一个很具体的矛盾， Miko 想做约定式、零配置框架，但原来的配置、入口和运行方式让用户仍然不得不理解太多框架内部细节。

最典型的是配置入口。让用户维护 vite.config.ts，自由度很高， 但 Vite 的插件、入口、SSG 和 Miko 的内建能力会开始争夺所有权。再补一个 miko.config.ts，表面上解耦，实际上只是把冲突搬到了两份文件之间。

v1 选择把问题砍掉。CLI 是唯一执行入口，普通项目不需要任何配置文件；确实需要覆盖约定时， 只保留根目录可选的 miko.config.ts，并且严格分为 miko 和 vite 两个命名空间。 框架能力归框架，Vite 原生字段归 Vite，应用入口仍由 Miko 负责。

零配置不是没有配置能力。
它是把大多数正确决定，变成不需要用户重复做的决定。

另一个边界也在这一轮明确。Bun 是仓库的包管理器、workspace 管理器、脚本调度器和发布工具， 但不是应用与 CLI 的运行时前提。分发出来的 miko 命令走的是 Node.js + jiti，所以业务项目不会因为选择这个框架而被绑定到 Bun runtime。

02

一个配置入口，背后是一条确定的解析链路。

约定式框架最怕的不是默认值多，而是默认值不可解释。Miko 因此不让每个插件各自扫描项目， 而是先构造唯一的项目解析结果，再让所有构建命令、Doctor、Check 和插件装配共享它。

这段核心逻辑很短，但决定了整个框架的行为边界。配置文件加载与项目探测并行执行， 随后才解析能力图并验证最终项目。这避免了在模块顶层读取 process.cwd() 一类隐式状态，也让根目录可以被 CLI 明确传入。

packages/vite-plugin-miko/index.ts 
export async function resolveMikoProject(env) {
  const [loaded, signals] = await Promise.all([
    loadMikoConfig(env),
    inspectProject(env.root, env.mode),
  ])

  const capabilities = resolveCapabilities(
    loaded.config.miko ?? {},
    signals,
    env,
  )
  const project = resolveMikoConfig(
    loaded, env, getBundledTemplate(), capabilities, signals,
  )
  validateResolvedProject(project)
  return project
}

Vite 配置也不是简单的对象覆盖。Miko 先生成受保护的默认字段，例如真实 root、应用 input、 SSG 入口、路径别名和内置插件，然后使用字段感知的 mergeViteConfig() 合并用户的 vite 命名空间。别名、依赖预构建 include/exclude、插件数组都有各自的合并规则， 语义冲突会在 Vite 启动前失败。

优先级来源例子目的
1显式配置miko.whiteScreen: false用户清晰表达的意图永远优先。
2目录约定components/、layouts/、Uno 配置让项目结构成为低摩擦配置。
3直接依赖Pinia、Vant、Element Plus依赖已经是最可靠的意图信号。
4当前命令DevTools 只在 miko dev 启用避免构建和预览携带开发成本。
5安全默认现代构建、应用内打包、SSG让新项目开箱即用，同时不引入隐式 CDN 风险。

Windows compatibility, discovered in final gates

最终 E2E 还发现了一个看似很小、实际会让零配置项目在 Windows 上失效的问题。 默认 localhost 会解析到 IPv6 的 ::1，而验收中的 Playwright 访问 127.0.0.1。v1 仅在 dev 命令默认生成 server.host: '127.0.0.1'，并让用户显式 vite.server.host 覆盖它。这个修复有回归测试，也经过真实浏览器验证。

03

Vite 需要 HTML 入口，但零配置不能靠复制临时文件。

这是 v1 里一个很容易被低估的工程细节。Vite 要从 HTML 入口开始，普通项目却不应该被强迫创建 index.html。旧方案会把模板复制到 node_modules 或临时目录，再把 Vite root 指过去。 这样虽然勉强能构建，却会破坏别名、静态资源、相对路径、用户 root 和 watcher 的语义。

新方案只保留真实项目 root。HTML 插件检查真实根目录是否存在 index.html，存在就完全使用用户文件；不存在时， 它通过 Vite 的 resolveId/load 在内存中提供同一个绝对路径身份的内容。 对 Vite 来说，它仍然是在加载项目根目录的 HTML；对用户来说，项目没有多出一个临时文件。

packages/vite-plugin-index-html/index.ts 
resolveId(id) {
  if (!hasUserHtml() && isHtmlId(id)) return htmlPath
  if (id === virtualModuleId) return resolvedVirtualModuleId
}

load(id) {
  if (!hasUserHtml() && isHtmlId(id)) return fallbackHtml
  if (id === resolvedVirtualModuleId) {
    return `import ${JSON.stringify(normalizePath(options.entry))}`
  }
}

这个设计还有两个重要收益。第一，用户 HTML 和内置 HTML 都经过同一条 transformIndexHtml 路径，Miko 可以可靠注入唯一的应用入口， 同时校验唯一 #app。第二，开发环境也能为非静态 GET/HEAD 请求提供 SPA history fallback，但资源请求和 API 请求不会被误吞成 HTML。

04

自动能力不是魔法，必须有一个能被 Doctor 展开的能力图。

Miko 的目标不是把几十个开关交给用户，而是尽可能根据项目事实做出正确选择。问题是， 如果每个插件自己检查依赖、自己读取文件、自己决定加载时机，最终一定会出现命令行为不一致、 扫描重复、加载顺序不稳定和诊断无从下手的问题。

所以 v1 先解析 ResolvedCapabilities。每一个能力不只记录 enabled，还记录 value、 source 和 reason。Doctor 不需要再猜插件到底为什么出现， 它直接展示决定本身。

这也让默认策略更清楚。CDN 只有显式给出 frameworkCDN 才会启用。Legacy 只有在 Browserslist 指向旧浏览器， 或用户显式配置时才会加载。Vue DevTools 只在 dev 命令进入插件链。检测到 Pinia 直接依赖就安装唯一实例， 检测到多个支持的 UI 库则直接报冲突，而不是静默选一个。

插件装配实现上先并行准备组件、UnoCSS、DevTools、Legacy、External、HTML、Janus 等独立组， 再按固定顺序写入 Vite 配置。这样减少了可选依赖的串行加载时间，同时避免了所谓随机插件顺序。 没有触发 CDN 时，也不会扫描或加载 framework 映射；禁用 UnoCSS 时保留空的 virtual:uno.css 占位，保证内置模板不会因为一个 import 缺失而崩掉。

05

运行时性能和可靠性，不能只在构建成功后靠祈祷。

性能优化做到了构建更快还不够。用户看到的是 HTML 什么时候出现、首屏什么时候绘制、 Vue 什么时候完成 hydration、切换路由是不是重新下载了一坨无关代码。更糟的是， 一旦入口脚本加载失败、bootstrap 抛异常或者 Suspense 永远不 resolve，用户看到的只有白屏。

Miko v1 选择了一条很克制的实现。默认 SSG 输出已有内容的 HTML，路由仍保持代码分割， 默认不走 CDN；Pinia 在 ViteSSG bootstrap 前安装唯一实例，页面 setup 创建的 store 状态在 onSSRAppRendered 后回写，客户端只恢复非空状态。这样既避免整条 SPA 路由被 ClientOnly 包起来，也避免手动注水导致的双实例或空 state。

为什么白屏监控必须是独立资源

最初很容易想到，在 HTML 里多注入一个 virtual module，让它负责监控。但 Vite 会把同一页面的多个 module script 合并为一个 Rolldown chunk。要是应用入口本身加载失败，监控也会跟着一起失效，等于在最需要它的时候没有它。

最终实现把监控做成独立 Vite asset。构建阶段通过 emitFile 产出带内容哈希的 miko-white-screen-*.js，HTML 生成完成后再替换占位 URL。 开发阶段由 /@miko/white-screen.js 中间件提供同样的模块。 它不依赖应用代码、不使用内联脚本或内联样式，因而更适合 CSP 严格的部署环境。

independent boot protocol, simplified 
let status = 'pending'

const fail = (code, value) => {
  if (status !== 'pending') return
  status = 'failed'
  renderFailure(code, detailOf(value))
}

window.__MIKO_BOOT__ = {
  get status() { return status },
  ready,
  fail,
}

window.addEventListener('error', onError, true)
window.addEventListener('unhandledrejection', onUnhandledRejection)
timer = setTimeout(() => fail('MIKO_BOOT_TIMEOUT'), 8000)

运行时 bridge 的职责非常小。Vue 首次路由渲染完成后调用唯一的 markMikoReady() 协议，监控移除 v-cloak 并标记 data-miko-ready="true"。在 ready 之前，bridge 会转发 Vue error、 hydration mismatch warning 和用户原有的 handler；ready 之后不再把正常运行期错误错误归类为启动白屏。

A small but important contract

默认白屏超时是 8000ms。false 可以关闭； 对象只覆盖 timeout。小于 1000 或非有限值会在启动 Vite 前以 MIKO_CONFIG_INVALID 拒绝，不把明显无效配置推迟到浏览器里发现。

06

把发布验收做成 miko check，而不是发一张人工 checklist。

构建成功只说明打包器没有报错。它不能证明生成的 HTML 有唯一 #app，不能证明静态资源存在，不能证明 deepest route 能启动， 更不能证明 hydration 警告、入口失败和永久 v-cloak 会被发现。

miko check 的关键设计是隔离输出目录。它在系统临时目录创建 outDir， 以当前 root 和 mode 执行同一条类型检查、项目解析、SSG 或 SPA 构建、静态校验和部署清单生成路径， 然后启动 Vite Preview 与 Chromium。正式的 dist 不会被覆写，完成或失败后临时目录都会清理。

packages/cli/check.ts 
const isolatedOutDir = await createTemporaryDirectory()
try {
  const result = await buildApplication(context, {
    outputOverride: isolatedOutDir,
  })
  await runBrowserCheck(result, context.allRoutes)
} finally {
  await remove(isolatedOutDir)
}

静态校验会递归检查真实 HTML，但不跟随符号链接；它检查唯一 app 容器、非空页面、v-cloak 与监控协议、 Vite error overlay、同源 script/stylesheet/modulepreload/preload 引用，以及非根 base 的资源映射。 静态问题统一返回 MIKO_BUILD_STATIC_CHECK 与退出码 5。

浏览器检查默认检查首页、最深产物路由和缺失路由， --all-routes 则读取 dist/.miko/routes.json 逐条检查。每条路由都会收集文档状态、关键资源失败、 page error、hydration warning、启动失败码、ready 标记和残留 v-cloak。任何浏览器问题统一以 MIKO_CHECK_BROWSER 和退出码 6 退出。

正常路径

空页面、ClientOnly、首页、最深路由和缺失路由必须能给出合理状态。

入口资源缺失

删除应用 entry 后，浏览器检查必须报告 MIKO_CHECK_RESOURCE。

Bootstrap 抛错

启动错误不能只留在 console，必须以 exit code 6 让 CI 感知。

永久 Suspense

超时后不能继续留着骨架，白屏协议应触发失败面板与稳定问题码。

07

迁移工具不是文本替换器，尤其不能为了读配置去执行旧配置。

允许破坏性大版本，不代表允许迁移器破坏用户项目。旧的 vite.config.ts 和 flat Miko 配置可能包含函数、条件表达式、对象展开、 顶层副作用或自定义插件顺序。直接 import 它们最危险的一点，不是解析失败，而是会真的执行用户代码。

miko migrate 默认只用 oxc-parser 做静态 AST 分析。静态字面量能被映射到新的 { miko, vite } 配置；函数、条件值、未知 spread、自定义插件顺序、 Miko 所有权 input 和跨来源冲突则变成明确的人工处理项。默认命令只输出 plan，绝不改文件。

只有 plan 完全安全时，--write 才会开始动作。它会在 .miko-migrate/<UTC timestamp>/ 独占创建备份，复制所有源文件， 写入带 PowerShell 与 POSIX 精确恢复命令的 RECOVER.md，再以 open(wx) → write → fsync → close → rename 做原子目标替换。

迁移场景行为为什么
零配置项目成功 no-op没有配置文件本来就是 v1 的理想状态。
可静态分析的 Vite wrapper生成统一 miko.config.ts保留可确定的 Vite 原生字段和 Miko 能力字段。
动态或条件配置拒绝写入，退出码 7宁可用户人工确认，也不能猜测函数在某个 mode 下的行为。
目标文件已存在拒绝覆盖，退出码 7没有备份来源归属时，不能碰用户拥有的目标文件。
写入后 --checkDoctor + 完整 Check迁移不是生成文件结束，必须复用同一个验收链路。

08

性能数字要能解释，否则它只是一次恰好跑得快的截图。

性能包是私有 Bun workspace，但被测的 CLI 和每次实际构建都由 process.execPath 启动 Node worker。这样测到的不是 Bun 在当前机器上的偶然优势， 而是分发后 Node + jiti 真实执行链路的表现。

每次 perf:check 生成 Small、Medium、Large、Runtime 四类 fixture。 每类采集 3 次 cold build、5 次 warm build，Runtime 再采集 5 次 375 × 812 Chromium 浏览器样本。 cold 会清理 dist、.miko-cache 与 .vite-ssg-temp；warm 只清理 dist。最终保留原始 samples，用中位数比较。

白屏监控带来了一个必须正视的边界

独立监控脚本会增加 1 个资源、1 个请求和每页一个 script 标签。第一次完整 gate 运行时， 原有基线还没有这项能力，于是 small fixture 的 asset count 从 11 到 12、运行时请求从 7 到 8， 低基数下看起来像 9.09% 与 14.29% 的回退。数字没有错，判断错了。

修复不是把基线偷偷刷新，也不是把所有预算放宽。性能比较器现在单独采集 whiteScreenMonitorAssetCount、 htmlPageCount 和 whiteScreenMonitorRequestCount。 它只允许每个构建 fixture 恰好一个监控 asset、运行时恰好一次监控请求，并给每个 SSG HTML 最多 128 bytes 的监控标签固定预算。监控脚本本身的 JS 体积、其余资源、传输、执行和路由性能仍然受原来的 5% gate 约束。

packages/performance/compare.ts, simplified 
const WHITE_SCREEN_MONITOR_TAG_BYTES = 128

const monitorCount = addedMonitorCount(
  before.whiteScreenMonitorAssetCount,
  after.whiteScreenMonitorAssetCount,
)
const monitorHtmlAllowance =
  monitorCount * (after.htmlPageCount ?? 0) * WHITE_SCREEN_MONITOR_TAG_BYTES

compareNumber(..., 'htmlBytes', ..., monitorHtmlAllowance)
compareExactNumber(
  comparisons,
  'runtime.whiteScreenMonitorRequestCount',
  current.runtime.whiteScreenMonitorRequestCount.median,
  1,
)

这是一个很小的实现，但它把性能指标从单一比例判断变成了更接近真实工程约束的模型。 可靠性能力的已知、不可避免成本可以被显式计量；任何额外的资源、重复监控或其它回退仍会失败。

框架最终卖的不是功能数量，
而是更少猜测，更多确定性。

Miko v1 没有试图重造 Vue、Vite 或浏览器平台。它做的是把成熟生态的正确使用方式收敛成更少的项目决策， 再把每一个自动决定、每一条失败路径和每一分性能代价纳入可观察、可测试、可恢复的工程闭环。

现在版本边界、迁移路径、性能基线、浏览器验收和发布包都已经准备完成。下一步不是继续往框架里塞能力， 而是按既定流程完成真实 npm 发布，让这条链路接受真实项目的使用反馈。

Design principle

CLI 唯一入口，零配置是默认能力，不是一个需要先配置才得到的模式。

Runtime boundary

Bun 负责仓库和发布，Node + jiti 承担分发 CLI。应用运行时不依赖 Bun API。

Honesty clause

所有性能数字来自同机 fixture，不承诺业务项目一定获得同样绝对毫秒数。
